## Causes established by the same requests

The instrumented baseline homepage after confirmed natural suspension took **2,512.778 ms TTFB**. Exact trace and provider request IDs correlate these overlapping observations:

| Observation | Duration / result |
| --- | --- |
| Provider function start | Cold; aggregate cold-start metric 378 ms |

| Instrumentation registration | 9.871 ms |
| Application handler / render | 1,211.873 / 1,200.374 ms |
| Blocking inventory-policy dependency | 1,025.776 ms |
| Two new DB connections | 862.713 / 948.193 ms |
| Neon resume inside the request window | 489 ms operation |
| Three SQL round trips | 32.797–96.396 ms |
| Observed pool waiting | Zero |

The immediate three repeats reused connections on the same measured instance: handler 42.703–79.347 ms, SQL round trips 2.882–10.571 ms and TTFB 325.989–403.587 ms. Connection establishment and resume were substantial contributors to the first public shell response. These nested/concurrent intervals must not be added, and subtracting the warm median does not isolate Neon activation.

A separate first traced deployment request opened seven connections in 164–363 ms while Neon was already active. Connection cost therefore also exists without a resume. The corrected production product trace later measured a 315 ms handler, two new connections of 74/124 ms, SQL round trips of 2–83 ms and zero pool waiting. Its first-probe flag was true while Vercel classified the function as hot: a fresh browser or first instrumentation event is not proof of a cold function.

Product clicks exposed a separate client delay. Before the change, the URL changed while neither catalog nor product was visible for 306–325 ms. Removing the redundant route loading boundary eliminated that observed interval in all three matched final runs. Existing disabled prefetch behavior was preserved; a network-prefetch change is not the explanation for this gain.

The final release's first post-promotion response was a slower **810 ms**, with no overlapping Neon resume. Vercel recorded 638 ms of prerender delivery and a separate cold background regeneration. These records do not fully explain the delivery outlier, and the background function's duration cannot be added to foreground TTFB.

## Implemented fixes

- The complete public homepage now uses prerendering/ISR with a 60-second refresh interval. Header, hero and all eight categories arrive in HTML. Admin and other commercial routes remain explicitly dynamic; client cart behavior and authoritative price/stock checks remain intact.
- Existing save-time invalidation preserves next-read freshness. Literal homepage path invalidation now matches the commercial route group's cache tags. Strict prerender guards reject configuration/data fallbacks after a failure rather than publishing incomplete cached content.
- The product layout awaits catalog shell data and returns the shell directly, with no additional Suspense boundary. The redundant product route `loading.tsx` is removed. Navigation retains the previous URL/content until complete product content commits; interruption tests verify abandoned transitions cannot publish stale products.
- Footer selection uses the actual route segment. Vercel background ISR uses internal canonical path `/index`; the former raw-pathname comparison produced a second server footer and React 418 during regeneration. The fix covers that installed Next route context and passed actual production expiry.
- Bounded opt-in instrumentation captures registration, pool acquisition, connection/query round trips, selected Next phases, dependencies and observed cache refreshes. Safe summaries run through `after()` without diagnostics database writes on the response path. It records no SQL, parameters, customer content, secrets or sessions. The final deployment explicitly sets `ATEHNA_PERFORMANCE_DIAGNOSTICS=0` for build and runtime.
- CI builds against disposable PostgreSQL. A guarded, authenticated local-only E2E reset regenerates copied homepage output against each shard's database/assets, retaining one shared compiled build. Production returns 404 for this endpoint.

A preliminary optimization candidate was rolled back after detecting a hydration error and intermittent initial-catalog delay. Its measurements remain preserved as rejected-candidate evidence and are excluded from the final public performance comparison below. The separately qualified admin series used that candidate with unchanged admin code.

## Limits and exact next actions

Pure SQL execution and lock waits, individual database DNS/TCP/TLS/auth steps, platform provisioning substeps, and physical display paint remain unmeasured. Zero observed pool waiting does not imply zero lock time. Cache lookup duration does not prove a cache hit; background regeneration can omit the incoming trace, and missing events are not zero-duration phases. Service/client UTC clocks were not calibrated; exact request/trace IDs identify correlations and durations are interpreted within their own clocks.

The matched product delay is resolved in measured runs. Homepage runtime dependence is removed from complete cached-response delivery, but the final 810 ms delivery outlier remains only partly decomposed. No compute, suspension or pooling change is justified. If that outlier recurs, collect normal request IDs with timing and inspect the provider's foreground prerender-delivery stage; do not infer Neon activation from TTFB. A larger authorized orders dataset is needed before evaluating large-list admin performance; mutations belong in an isolated copy. Keep optional diagnostics off unless another bounded investigation needs them.

All authorized implementation and required verification are complete. No further deployment, paid change or user action is required for this pass. Remaining work is conditional on recurrence of the identified delivery outlier or availability of a representative larger admin dataset; neither is a demonstrated unresolved application regression.
